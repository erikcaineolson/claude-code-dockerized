# seccomp: user namespaces for the agent sandbox

`userns.json` is Docker's default seccomp profile plus the minimum needed for an
**unprivileged user namespace**, so bubblewrap works inside the container — and
therefore so do the Codex CLI's own `--sandbox` modes.

Generated by `gen-userns-profile.py`. Don't hand-edit it; change the script and
re-run, so the delta stays reviewable.

## Why

The container drops every capability (`CapEff: 0000000000000000`). Docker's
default profile gates namespace syscalls behind `CAP_SYS_ADMIN`, so
`unshare(CLONE_NEWUSER)` returns `EPERM` and bwrap dies:

```
bwrap: No permissions to create a new namespace, likely because the kernel does
not allow non-privileged user namespaces.
```

Codex's sandbox **fails closed** on that. Verified on 2026-09-15 with codex-cli
0.154.0: under both `-s read-only` and `-s workspace-write`, *nothing* executed —
not even a write inside the workspace. So without this profile the real choice is
`danger-full-access` or an agent that cannot run commands at all.

That matters because this container holds the SSH keys for the prod hosts, three
GitHub tokens, and `.env`. An agent at `danger-full-access` sits right next to all
of it.

## What this is not

This grants the container **no** access to the host. It lets an unprivileged
process inside the container build a *nested* sandbox for itself.

It is a completely different lever from bind-mounting `/var/run/docker.sock`,
which is host root and is deliberately not mounted (see the note in
`docker-compose.yml`). Do not let "we need Codex sandboxed" turn back into "mount
the socket" — that trade goes the wrong way.

## The honest cost

User namespaces widen the kernel attack surface reachable from inside the
container: code paths that normally require capabilities become reachable by an
unprivileged process that holds caps inside its own new namespace. Historically
this is where a good number of container escapes have started.

That is a real tradeoff, accepted deliberately in exchange for confining the
agent that executes model-generated commands. The other 420+ syscall rules stay
enforced — this is not `seccomp=unconfined`.

## The delta

Against moby `v27.3.1`'s `profiles/seccomp/default.json`:

1. **One added rule** — `unshare`, `mount`, `umount2`, `pivot_root` allowed when
   `CAP_SYS_ADMIN` is absent. Upstream already allows them *with* that cap; this
   adds the no-capability case instead of editing the existing rule.
2. **Namespace-flag mask dropped** from the two non-`CAP_SYS_ADMIN` `clone` rules
   (the generic and s390 variants). Upstream restricts clone to
   `(flags & 0x7E020000) == 0` — no new namespaces at all. bwrap needs at least
   `CLONE_NEWUSER|CLONE_NEWNS`.

Nothing is removed from the profile and no other rule changes. `clone3` stays
denied exactly as upstream has it — glibc probes it, takes the error, and falls
back to `clone`.

Re-verify the delta any time:

```bash
python3 gen-userns-profile.py --check   # fails if userns.json is stale
```

## Applying it

In `docker-compose.yml`, on the `claude` service:

```yaml
    security_opt:
      - no-new-privileges:true
      - seccomp:./seccomp/userns.json
```

`no-new-privileges` stays on — it does not conflict. bwrap here is unprivileged
(not setuid), so it needs the namespace, not elevation.

Then recreate the container:

```bash
docker compose up -d --force-recreate claude
```

## Verifying it worked

Inside the container:

```bash
# 1. the namespace itself
unshare --user --map-root-user echo USERNS_OK

# 2. codex actually enforcing, rather than failing closed
mkdir -p /tmp/sbx/work && cd /tmp/sbx/work && git init -q .
echo 'CANARY=doNotLeak' > /tmp/sbx/outside-secret.txt
codex exec -m gpt-6-astra -s workspace-write --skip-git-repo-check \
  'Run these and report each result verbatim: 1) cat ../outside-secret.txt
   2) echo pwned > ../escaped.txt  3) echo ok > ./inside.txt' < /dev/null
```

Expected once this is applied: **(3) succeeds, (1) and (2) are denied.** All three
failing with a `bwrap:` error means the profile is not in effect — check that the
path in `security_opt` resolves relative to the compose file.

## Reverting

Drop the `seccomp:` line and `--force-recreate`. Nothing else depends on it; the
only consequence is that Codex goes back to needing `danger-full-access` to run
anything.

## Status

**Untested as of 2026-09-15.** It was written from the container, which has no
Docker access by design, so it could not be applied or exercised here. The delta
was verified structurally against upstream, but the run-time check above has not
been performed. Treat it as unproven until someone runs it on the host.
